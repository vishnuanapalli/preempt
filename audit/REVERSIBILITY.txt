Migration reversibility — 2026-07-30
====================================

WHAT THIS IS: the record of *how* migration reversibility is established here, and what it
does not establish. **It deliberately contains no test counts, line counts or ratios.** Three
consecutive review rounds found a wrong number in this file, and each correction was stale
before the commit landed — including one that said "verified by running it, not inferred"
next to a figure that was neither. A snapshot artifact holding live values is the rot the
2026-07-28 friction entry ruled against, and correcting the numbers a fourth time would have
been treating the symptom.

For current numbers, run the commands. They are the source; this file is the reasoning.

    docker compose up -d --wait
    cd api && uv run pytest tests/test_reversibility.py
    ./scripts/verify.sh                    # section 4 prints the verification/application ratio


The problem this replaced
-------------------------

S-002 asked for `alembic downgrade base` then `upgrade head` to succeed. That exits 0 against
a migration whose `upgrade()` and `downgrade()` are both `pass` — which is what the baseline
was — and it was reported as demo evidence. The useful question is never "did the command
succeed" but "would this notice if the thing it checks were untrue".


How it is established
---------------------

The schema is read from the database before and after. Reversible means reversing leaves it
indistinguishable from before, and re-applying produces what it produced the first time. Four
object classes — relations, columns, indexes, constraints — because those are what a migration
creates. `alembic_version` and extension-owned objects are excluded for correctness: the first
survives `downgrade base`, and the local image ships timescaledb.

Failability is tested, not asserted. Two deliberately broken migrations run on every gate
invocation: one that drops nothing on downgrade, one that raises on upgrade. Each fix to this
harness is verified by reverting it and requiring the suite to go red.

**Two pins exist because a floor alone is satisfiable by a constant.** `covered` is bounded
below by twice the model table count *and* above by an exact-equality assertion on a
hand-built snapshot; `head_classes` is bounded the same way. Both counterweights were added
after review found that a constant satisfied the one-sided version — twice, in the same file,
by the same mechanism.

Since S-010 this covers real schema. Before it, `covered` was 0 and a strict xfail said so;
that marker failed the day the tables landed, which is what it was for, and it is gone.


What it does not establish
--------------------------

- **The depth of the four classes.** Definitions are compared, but nothing proves a change
  *within* a class would be caught; that needs a fixture the 2026-07-29 trim removed.
- **The NULL-definition guard in `_read_snapshot`.** Nothing exercises it.
- **Row data, grants, ownership, comments, triggers, policies, types, routines, view and
  sequence internals, TimescaleDB-specific objects, branched histories.** A downgrade that
  destroys a table's contents while restoring its shape reads as reversible here.
- **Anything about Neon.** The round trip runs against the local container on 5434 only.
- **That it cannot run against the application database — only that it refuses to.** The
  check compares host, port and database name with loopback spellings folded together, and
  when `PREEMPT_DATABASE_URL` is unset it requires the target to be loopback. `Settings` is a
  weaker thing and was once cited here as if it were this one: it compares two strings, so it
  passes for `localhost` against `127.0.0.1`, and it does not run at all when the application
  URL is unset.
- **Reversibility anywhere a database is absent.** These tests skip with a reason naming what
  is unproven. CI provisions the database as of `41b1e85`, so they run there.


Two destructive defects this harness has had, both found by review
------------------------------------------------------------------

Recorded because both were introduced by *fixing* something, which is the pattern worth
remembering rather than the individual bugs.

1. **Cleanup that stamped instead of migrated.** `command.stamp(real_head)` claims a revision
   is applied rather than applying it. Harmless against an empty baseline; once S-010 created
   real tables it told alembic the migration was in place while its tables were gone, and
   every later run died on `DROP TABLE price_metric`. Replaced by a reset that drops public
   tables, clears `alembic_version` by SQL, and upgrades for real.

2. **A fixture that destroyed the target before the guard ran.** That reset was then wired in
   as `autouse`, so it ran `DROP TABLE ... CASCADE` over every table in `public` *without*
   passing through the database-identity guard — making it strictly more destructive than the
   `downgrade base` the guard exists to prevent, since it drops tables no migration created.
   Demonstrated on a throwaway database: every table gone, not one guard message printed. The
   guard had already been fixed twice; it was bypassed by code added in the same commit as its
   second fix. The fixture is now requested explicitly and goes through the guard first.
